# すすみ（Susumi）第1段階 設計書

- 作成日: 2026-10-31
- 元になった資料: `claude_code_指示書_福祉施設共有記録.md`（以下「指示書」）、`AGENTS.md`
- この設計書は指示書の内容を一部変更している。食い違う場合はこの設計書を優先する。変更点は「指示書からの変更点」にまとめた。
- 2026-11-04変更: Windowsの確認はCIのみで行い、依頼者による実機確認を完了条件から外す。【決定】

表記の約束:
- 【決定】は依頼者が決めたこと
- 【判断】は設計者が決めたこと。依頼者が設計書を読んで確認する前提で置いている
- 【実装者に任せる】は実装者が決めてよいこと

## 1. 何のためのものか

依頼者は福祉施設の職員である。今はGoogleカレンダーとスプレッドシートで仕事を共有しているが、次の問題がある。

- どこを見ればよいのかわかりにくい。
- 更新を忘れる。依頼者自身も、細かく分かれた作業の進み具合がわからなくなった。
- 利用者さんの作業工程の進み具合を、担当の職員しか知らない。たとえば写真作業を3人ほどの利用者さんに同時に頼んでいるが、ほかの職員には状況がわからない。
- 以前はホワイトボードで管理していた。

このシステムでは、進み具合を見る場所と更新する場所を一つにまとめる。そのうえで次の状態を目指す。

- 職員は、ボードを開けば、どの利用者さんがどの作業のどの段階にいるかがわかる。
- 利用者さん本人も自分のパソコンで「今日の作業と進み具合」を見て、自分で更新できる。
- 更新はボタン1回かドラッグ1回で終わる。そのため更新を忘れにくい。
- 誰かが更新すると、ほかの人の画面にもすぐ反映される。

依頼者は、ほかの施設でもこのシステムを使えるようにしたいと考えている。【決定】

## 2. 利用者と環境

- 職員: 複数人。全員がすべての職員ボードと、利用者さんの進捗を見られる。【決定】
- 利用者さん: パソコンを一人一台使う。パソコン操作は全員できる。【決定】
- 同時接続はおよそ8人まで（指示書）。
- 施設のLAN内だけで使い、インターネットには公開しない（指示書）。
- サーバーにするパソコンはWindowsが圧倒的に多い。macOSを使う施設もあるので、macOSでも動かす。【決定】
- 設置はワンクリックでできるようにする。【決定】
- ほかの施設には、漢字が読めない利用者さんもいる。【決定】
- 依頼者は、このソフトとサービスを販売して事業にしたいと考えている。ただし初期の利用施設はほとんどない見込み。【決定】
- Googleカレンダーなど外部サービスがなくても使える。【決定】
- 画面の文言は日本語にする。

## 3. 目標・目標外・失敗条件

### 第1段階の目標【決定】

1. ログイン
2. 利用者さんのホーム画面
3. Kanban（作業ごとのボード）

この3つがそろえば、施設で使い始められる。

### 第1段階では作らないもの（第2段階以降）【決定】

- 共有ノート。第2段階で「利用者さん向け」と「職員向け」に分けて作る。
- チーム機能。利用者さんをチームに分け、同じチームの人の進捗を見せる。チームの追加・削除・修正は簡単にできるようにする。
- カレンダー表示。月・週ごとに、いつ・誰が・何をするかを一覧する。
- 閲覧者の表示（Presence）。

第1段階の設計は、これらを後から追加しやすい形にしておく。具体的には、アカウントに役割を持たせること、ボードや列に見える範囲を持たせること、カードに予定日を持たせることを、最初から入れておく。

### 目標外（予定もしない）

- インターネットへの公開、外部サービスとの連携
- 1つのサーバーで複数施設を扱うこと。施設ごとに1台のサーバーを置く。【判断】
- CRDTによる完全な同時編集（指示書）
- モバイルネイティブアプリ（指示書）

### 失敗条件（動いていても失敗とみなすもの）

- 利用者さんが職員専用ボードや職員用の列の内容を見られる。URLを直接入力した場合も含む。
- サーバーを再起動するとデータが消える。
- 設置に専門知識が必要になる。Elixirやデータベースを別途インストールする必要がある、など。
- 動かすのにインターネット接続が必要になる。
- 利用者さんの画面が複雑で、本人だけでは更新できない。
- 更新に何度も操作が必要で、結局更新を忘れる。

## 4. 技術の前提

- Phoenix LiveView、SQLite（`ecto_sqlite3`、WALモード）、Phoenix PubSubを使う（指示書）。
- JavaScriptはSortable.jsのLiveView Hookと、LiveView標準機能の範囲に留める（指示書）。
- 実行時に外部ネットワークへアクセスしない。CDNとWebフォントは使わない（指示書）。
- 開発はmacOSで行う。配布先は主にWindowsで、macOSにも配布する。

## 5. 機能の詳細

### 5.1 初回設定

- 初回起動時にアカウントが1件もなければ、初回設定画面を表示する。そこで施設名と最初の職員アカウントを作る。【判断】
- 施設名は画面のヘッダーに表示する。施設固有の情報はプログラムに書き込まず、画面から設定する。【判断】
- 初回設定が終わったら、この画面には二度と入れないようにする。

### 5.2 アカウントとログイン

アカウントの種類【決定】
- 役割は「職員」と「利用者」の2種類。
- 職員にも利用者さんにも、一人ずつ別のパスワードを付ける。

ログインの流れ【決定】
1. 「職員」か「利用者」を選ぶ。
2. 名前を一覧から選ぶ。
3. パスワードを入力する。

アカウントの管理【判断】
- アカウントの作成、パスワードの再設定、無効化は職員が行う。
- アカウントには、名前のほかに「よみ（ひらがな）」と「ふりがなを表示する」の設定を持たせる。詳しくは5.5。
- 利用者さんが自分でパスワードを変える機能は作らない。
- ログイン画面の名前一覧には、有効なアカウントだけを出す。LAN内で使うので、名前が一覧に出ることは許容する。
- アカウントを削除すると、担当していたカードの扱いが複雑になる。そのため削除はせず「無効化」にとどめる。

パスワードの条件【判断】
- 利用者さんは4文字以上。数字4桁でもよい。
- 職員は8文字以上。

ハッシュ化【判断】
- `pbkdf2_elixir` を使う。理由は、NIFを使わない純粋なElixirの実装なので、Windows向けにまとめるときにつまずきにくいからである。

職員が全員締め出されないための仕組み【判断】
- 有効な職員アカウントが1件だけのときは、そのアカウントを無効化できないようにする。
- 職員全員がパスワードを忘れた場合に備えて、復旧の手段を用意する。サーバーにしているパソコンで復旧用の起動方法（例：起動オプションや復旧用ショートカット）を使うと、そのパソコン（`localhost`）からだけ職員のパスワードを再設定できる。具体的な起動方法は【実装者に任せる】。手順書にも書く。

ログインの失敗回数の制限【判断】
- 同じアカウントで続けて5回失敗したら、5分間ログインできないようにする。
- 回数はメモリ上で数えればよく、再起動したらリセットされてかまわない。

ログイン状態を保つ時間【判断】
- 利用者さんはパソコンが一人一台なので、ログインした状態を30日間保つ。
- 職員は、席を離れたときのことを考えて、60分間操作がなければログアウトする。この時間は設定で変えられるようにする。

### 5.3 ボード・列・カード

指示書のスキーマをもとに、次のように変える。

**ボード（`kanban_boards`）**

- `board_type` は必須にする。【判断】指示書では任意だったが、見える範囲を決める項目になったため。
  - `"user_progress"`（利用者作業）: 写真作業など、作業ごとに職員が作る。利用者さんは、ここにある自分のカードだけを、ホーム画面を通して見る。
  - `"staff_task"`（職員専用）: 職員の事務作業用。利用者さんには一切見せない。
- `staff_task` のボードに作れる列は、職員用の列（`column_type = "staff"`）だけにする。【判断】

**列（`kanban_columns`）**

- 列は作業の段階にあたる。たとえば「受け取り｜選別｜補正｜仕上げ」。【決定】
- `column_type`（`"user"` か `"staff"`）は必須。【決定】
- 利用者さんには、職員用の列の名前も中身も見せない。【決定】
- 一番右の列（`position` が最大の列）を「完了」とみなす。【判断】
- 完了の列にあるカードは、利用者さんのホーム画面に出さない。
- 列の追加、名前の変更、並べ替え、削除は職員が行う。カードが残っている列は削除できないようにする。【判断】

**カード（`kanban_cards`）**

指示書では担当者を文字列で持っていたが、アカウントへの外部キーに変える。【判断】

| 項目 | 内容 |
|------|------|
| `title` | 必須 |
| `description` | 任意 |
| `assignee_id` | 担当の職員。任意 |
| `related_user_id` | 担当の利用者さん。任意。`user_progress` のボードでだけ使う |
| `scheduled_on` | 予定日（日付）。任意 |
| `position` | 列の中での順番。0から始まる連番 |
| `column_id` | 所属する列 |

- カードを作成・編集・削除できるのは職員だけ。【判断】
- 利用者さんは、自分のカードを「進める」「戻す」だけができる。
- 職員の画面では、ドラッグ＆ドロップでカードを動かせる（指示書）。キーボードでも動かせるよう、移動ボタンも付ける（AGENTS.md）。
- 移動したら `position` を計算し直して保存する。移動の計算方法はAGENTS.mdに従う。

**職員のボード画面での表示**

- 利用者用の列と職員用の列を、色と文字ラベルの両方で区別する（指示書）。
- 利用者用の列のカードには、担当の利用者さんの名前を出す。職員用の列のカードでは、担当の職員の名前を強調する（指示書）。
- 予定日を過ぎていて、まだ完了していないカードは目立たせる。【判断】

### 5.4 利用者さんのホーム画面（ブレインストーミングの案A）【決定】

ログインした利用者さんに表示する画面。

**表示するカード**

- すべての `user_progress` ボードから、`related_user_id` が自分で、完了の列にないカードを集める。

**画面の並び**【判断】

1. 「今日やる作業」
   - 予定日が今日のカード。
   - 予定日を過ぎて終わっていないカードもここに入れ、「予定日を過ぎています」と目立たせる。
2. 「そのほかの作業」
   - 予定日がないカードと、予定日が明日以降のカード。
   - 予定日がある順に並べ、予定日のないものは最後に置く。

「今日」は、サーバーにしているパソコンの現地時刻で決める。【判断】

**1枚のカードに出すもの**

- 作業名（カードの `title`）と、ボード名。
- 段階の目印。ボードの利用者用の列を左から順に並べ、今いる段階まで「●」、それより後を「○」で示す。今の段階の名前も文字で出す。
- 職員用の列は目印に含めない。カードが職員用の列にあるときは「職員が確認中」と表示する。【判断】
- ボタンは「次の段階へ」と「一つ戻す」の2つ。

**ボタンの動き**【判断】

- 「次の段階へ」: カードを、`position` の順で右隣の列の末尾へ動かす。
  - 右隣が職員用の列でも動かせる。利用者さんの作業が終わり、職員へ引き渡す場面を想定している。
  - 右隣が完了の列なら、カードはホーム画面から消える。消える前に「完了しました」と短く表示する。
- 「一つ戻す」: カードを左隣の列の末尾へ動かす。
  - 左隣が職員用の列なら戻せない。
  - 一番左の列にあるときも戻せない。
- カードが職員用の列にあるときは、どちらのボタンも使えない。
- 押し間違えたときは「一つ戻す」で元に戻せる。この操作に確認ダイアログは出さない。

**画面の見た目**

- 文字とボタンを大きくし、押しやすくする。
- キーボードでも操作できるようにする。
- 色だけで状態を伝えない。

### 5.5 ふりがな【決定：漢字が読めない利用者さんに対応する】

方針【判断】
- 利用者さんのアカウントごとに「ふりがなを表示する」を設定できる。職員が切り替える。
- この設定がオンの利用者さんの画面では、次のものに `<ruby>` でふりがなを付ける。
  - 画面の固定の文言。「今日やる作業」「次の段階へ」「一つ戻す」「職員が確認中」など。
  - 名前、ボード名、列名（段階の名前）、作業名。
- ログイン画面では、まだ誰がログインするかわからない。そのため、次のものには常にふりがなを付ける。
  - 「職員」「利用者」の選択肢
  - 利用者さんの名前の一覧
  - 「パスワード」などの文言

データの持ち方【判断】
- 次の項目に「よみ」を持たせる。いずれも任意の入力欄とし、空のときはふりがなを付けずに表示する。

  | 持たせる場所 | 項目 |
  |------|------|
  | アカウント | `name_kana` |
  | ボード | `name_kana` |
  | 列 | `name_kana` |
  | カード | `title_kana` |

- よみの入力欄は、職員が名前や作業名を入力する画面に並べて置く。
- 漢字の自動ふりがな変換（形態素解析）は使わない。理由は2つある。外部辞書への依存が増えること、Windows向けにまとめるときに部品が増えること。
- よみは「語全体に1つ」付ける。漢字1文字ごとに分けて付けることはしない。たとえば「写真作業」に「しゃしんさぎょう」と付ける。

固定の文言
- 固定の文言は、やさしい言葉で書く。
- 固定の文言のよみは、プログラムの中に用意しておく。

### 5.6 職員の画面

- ボード一覧。「利用者作業」と「職員専用」を分けて表示する。
- ボード画面。ドラッグ＆ドロップができ、カードの作成・編集・削除と、列の管理ができる。
- アカウント管理。作成、パスワードの再設定、無効化ができる。
- 設定。施設名、データの保存場所の表示、バックアップの手順の案内。【判断】
- 利用者さんのホーム画面を、職員がその利用者さんの立場で確認できる表示。【実装者に任せる】あれば便利だが必須ではない。

### 5.7 リアルタイム反映

- 職員のボード画面で誰かがカードを動かしたら、同じボードを開いているほかの職員の画面にすぐ反映する。
- 利用者さんが「次の段階へ」を押したら、そのボードを開いている職員の画面にすぐ反映する。
- 職員がカードを動かしたり編集したりしたら、関係する利用者さんのホーム画面にすぐ反映する。担当の利用者さんが変わった場合は、変更前と変更後の両方に反映する。
- PubSubのトピックの切り方は【実装者に任せる】。AGENTS.mdの命名を基本にする。

### 5.8 アクセス制御

- 見える範囲の制御は必ずサーバー側で行う。LiveViewの `mount` と、すべての `handle_event` で役割と所有者を確認する。画面に出さないだけで済ませない。
- 利用者さんができることは、次の2つだけ。
  - 自分のホーム画面を見る。
  - 自分のカードを「進める」「戻す」。
- 利用者さんが次のものにアクセスしようとしたら、拒否してホーム画面へ戻す。
  - 職員専用ボード、ボード画面そのもの、アカウント管理
  - 他人のカード
- このアクセス制御はテストで担保する。

## 6. Windows・macOSでの配布と起動【決定：ワンクリック起動、Windowsが主でmacOSにも対応】

### 6.1 方針【判断】

- `Burrito` を使い、Elixirの実行環境まで含めた単体の実行ファイルを作る。
  - Windows向け（x86_64）
  - macOS向け（Apple Silicon と Intel）
- 設置する人は、実行ファイルをダブルクリックするだけで使い始められる。Elixir、Erlang、データベースを別にインストールする必要はない。
- macOSでも、Finderからダブルクリックで起動できる形にする。`.app` にするか `.command` を添えるかは【実装者に任せる】。
- 以降の6.2〜6.6はWindowsを基準に書いている。macOSで異なる点は6.8にまとめた。

### 6.2 起動したときの動き

- サーバーを `0.0.0.0` のポート4000で起動する。ポート番号は設定ファイルで変えられる。
- 起動すると、そのパソコンの既定のブラウザで `http://localhost:4000` を開く。
- コンソール画面に、同じLANのほかのパソコンから開くためのアドレス（`http://<このPCのIP>:4000`）を表示する。
- コンソール画面を閉じるとサーバーが止まる。このことをコンソールにも表示する。
- ポートが使用中で起動できないときは、わかりやすい日本語のメッセージを出す。

### 6.3 データの置き場所

- データフォルダは既定で `%LOCALAPPDATA%\Susumi\` とする。
- 中に入るものは次の3つ。
  - SQLiteのファイル
  - 自動生成した `secret_key_base`
  - 設定ファイル
- 初回起動時に自動で作る。
- 環境変数か設定で場所を変えられるようにする。
- データフォルダの場所は、職員の設定画面に表示する。

### 6.4 バックアップ

- 第1段階のバックアップ方法は「サーバーを止めてデータフォルダをコピーする」とし、手順書に書く。
- アプリ内のバックアップボタンは第2段階以降で検討する。

### 6.5 新しい版への更新【判断】

- 新しい版の `.exe` に置き換えて起動すると、必要なマイグレーションを起動時に自動で実行する。
- マイグレーションを実行する前に、データフォルダ内のSQLiteファイルの複製を自動で作る（ファイル名に日時を入れる）。
- アプリに版番号を付け、職員の設定画面とコンソールに表示する。
- 配布の経路（GitHubで公開するか、ライセンスをどうするか）は第1段階では決めない。

### 6.6 その他の設定

- LiveViewのWebSocketは、LAN内のIPアドレスでアクセスしても拒否されないようにする（`check_origin: :conn` など）。
- 初回起動時にWindowsのファイアウォールが通信の許可を求める。設置手順書に「プライベートネットワークで許可」を押すよう書く。
  - 管理者権限がないと許可できない場合がある。手順書に、その場合は施設のパソコン管理者に依頼するよう書く。
  - LANがWindowsで「パブリックネットワーク」扱いになっていると、ほかのパソコンからつながらない。手順書に、確認と変更の方法を書く。
- コード署名はしない。【決定】初めて開いたときに「WindowsによってPCが保護されました」という警告が出るので、手順書に「詳細情報 → 実行」と押す方法を書く。Windowsの警告画面の写真は必須にしない。販売が軌道に乗った時点で、コード署名を改めて検討する。
- Windowsの起動時に自動で立ち上げる設定は、手順書で任意の手順として案内する。たとえばスタートアップフォルダへショートカットを置く方法。

### 6.7 最初に行う確認（スパイク）

第1段階の最初の作業として、次のことを確かめる。

- 中身がほとんど空のPhoenixアプリに、`ecto_sqlite3`（WALモード）と `pbkdf2_elixir` を入れる。
- `Burrito` でWindows向けの `.exe` と、macOS向けの実行ファイルを作る。
- Windowsでの確認はGitHub ActionsのWindowsランナーで行う。【決定】ビルドした `.exe` の起動、HTTP応答、SQLiteへの書き込み、再起動後のデータ保持、LiveViewの2画面間の同期、二重起動時の案内を自動確認する。CIの成功を完了条件とし、依頼者の実機確認を待たない。
- Windowsのダブルクリック操作、SmartScreen、ブラウザの自動起動、施設のファイアウォール設定、同じLANの別PCからの接続はCIでは再現しない。検証範囲外として記録し、成功したものとして扱わない。
- macOSでの確認は実装者が開発機で行う。
- macOSの実機では、次がすべてできることを確認する。
  1. ダブルクリックで起動する
  2. SQLiteに書き込める
  3. 再起動後もデータが残る
  4. 同じLANの別のパソコンからアクセスできる
  5. LiveViewのリアルタイム更新が動く

ここで失敗した場合は、作り込む前に依頼者と方針を相談し直す。代わりの案は2つある。

- WindowsのCI（GitHub ActionsのWindowsランナーなど）で `mix release` をビルドし、起動用のバッチファイルかインストーラーを添える。
- 構成そのものを見直す。

`.exe` をどこでビルドするか（macOSからのクロスビルドか、WindowsのCIか）は【実装者に任せる】。

### 6.8 macOSで異なる点【判断】

- データフォルダは既定で `~/Library/Application Support/Susumi/` とする。
- ブラウザは `open http://localhost:4000` で開く。
- コード署名と公証（notarization）はしない。初めて開くときにGatekeeperの警告が出る。手順書に、次の手順を画面写真付きで書く。
  - 「システム設定 → プライバシーとセキュリティ → このまま開く」で起動を許可する。
- 初回起動時に、macOSのファイアウォールが受信接続の許可を求めることがある。手順書に「許可」を押すよう書く。

## 7. テスト

TDDで進める。進め方はAGENTS.mdに従う。第1段階では、特に次をテストする。

- ログイン
  - 正しいパスワードでログインできる。
  - 間違ったパスワードではログインできない。
  - 失敗回数の制限が働く。
  - 無効化したアカウントではログインできない。
- アクセス制御
  - 利用者さんは、職員専用ボード、ボード画面、アカウント管理、他人のカードにアクセスできない。
- ホーム画面
  - 「今日やる作業」と「そのほかの作業」に正しく振り分けられる。
  - 予定日を過ぎたカードが「今日やる作業」に入る。
  - 完了の列のカードは出ない。
  - 職員用の列のカードには「職員が確認中」と出る。
- 「次の段階へ」「一つ戻す」
  - 端の列、職員用の列、完了の列のそれぞれで、決めたとおりに動く。
- カードの移動
  - `position` の計算が正しい。境界値はAGENTS.mdに従う。
- リアルタイム反映
  - 職員同士の画面、職員と利用者さんの画面の両方向で反映される。
- ふりがな
  - 設定がオンの利用者さんの画面では、`<ruby>` が出る。
  - オフの利用者さんの画面では出ない。
  - よみが空の項目には、ふりがなを付けずに表示する。
- Windows
  - CIのWindowsランナーで単体実行ファイルを自動確認する。CIの結果と検証範囲外の項目を記録する。
- macOS
  - 実機で手動確認する。確認した内容と結果を記録する。
